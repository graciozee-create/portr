## 0. Как здесь работать (важно)

**Собрать локально нельзя.** В песочнице нет JDK, а сеть отрезана от Maven Central,
NeoForged Maven и Adoptium — всё это уже перепробовано, не трать время (детали в
разделе «Errors & Dead Ends» соседнего документа). Единственная проверка — CI на GitHub.

Цикл работы:

```bash
git add -A && git commit -m "..." && git push origin arena/019ff5e7-portr
sleep 165
gh run list --branch arena/019ff5e7-portr --limit 1 \
  --json databaseId,headSha,conclusion --jq '.[]|"\(.databaseId) \(.headSha[0:8]) \(.conclusion)"'
```

Сборка ~1.5–2 мин. **Обязательно сверяй `headSha` с `git rev-parse --short HEAD`** —
иначе легко принять зелёный прогон предыдущего коммита за свой.

Если сборка упала, логи Actions из песочницы недоступны (blob-хранилище блокируется).
Ошибки javac достаются только так:

```bash
ID=$(gh api repos/graciozee-create/portr/actions/runs/<RUN_ID>/jobs --jq '.jobs[0].id')
gh api repos/graciozee-create/portr/check-runs/$ID/annotations \
  --jq '.[]|select(.path|endswith(".java"))|"\(.path):\(.start_line): \(.message)"'
```

Ещё два предупреждения из опыта:

- **Токен GitHub может протухнуть посреди сессии** (`gh: Bad credentials`). Тогда просто
  продолжай работать локальными коммитами и попробуй запушить позже — он восстанавливается.
- **Воркспейс может быть переклонирован между сессиями.** Если `git log` показывает только
  1–2 коммита, а на удалённой ветке их 30+ — **не пушь с `--force`**. Сохрани свою правку
  патчем, сделай `git reset --hard FETCH_HEAD` и наложи патч сверху. Один раз это уже чуть
  не затёрло всю историю порта.
- `/tmp/orig` (клон оригинала) при этом тоже пропадает, восстанавливается так:
  ```bash
  git clone --depth 1 -b reworked-girls \
    https://github.com/colorgarden/Pleasure-Horizons-I18n.git /tmp/orig
  ```

## 1. Баг с уровнем отношений (подтверждён, чинить в первую очередь)

**Симптом от пользователя:** у девушки в интерфейсе показано «4/4», то есть максимум
достигнут, но сцена *Cowgirl* требует 10 уровень — недостижимо, контент заблокирован.

**Причина найдена.** В оригинале `maxRelationshipLevel()` — это **вычисляемый** метод:
он берёт максимальный `requiredRelationshipLevel` среди всех сцен девушки
(`/tmp/orig/.../entity/base/GirlEntity.java`, строки 362–385):

```java
int value = options.stream()
        .map(Scene::requiredRelationshipLevel)
        .max(Integer::compareTo)
        .orElse(4);
this.dataTracker.set(MAX_RELATIONSHIP_LEVEL, value);
```

В порту (`entity/base/GirlEntity.java:837`) это выродилось в простой геттер поля:

```java
public int maxRelationshipLevel() {
    return this.entityData.get(MAX_RELATIONSHIP_LEVEL);   // всегда 4
}
```

Поле инициализируется четвёркой (`builder.define(MAX_RELATIONSHIP_LEVEL, 4)`, строка 185),
а `setMaxRelationshipLevel(...)` **не вызывается вообще нигде** — проверено grep'ом по
всему проекту. Поэтому максимум навсегда 4.

У Мики (`entity/girls/MikaEntity.java`) сцены требуют 6, 8 и **10** — отсюда и «4/4»
при недостижимой Cowgirl.

**Что сделать:** вернуть вычисление максимума из `getScenes()`, как в оригинале.
Осторожно с двумя вещами:

1. `entityData.set(...)` **нельзя** дёргать с клиента — будет рассинхрон/исключение.
   В оригинале это Fabric-код, где вызов шёл с сервера. Либо считай значение на сервере
   (например, при `finalizeSpawn`/загрузке и при перезагрузке профилей), либо сделай
   метод чистым вычислением без записи в `entityData`, а поле оставь только для синка
   на клиент. Второй вариант безопаснее.
2. `getScenes()` у `CustomGirlEntity` читает JSON-профиль, который грузится на
   `ServerStartingEvent`. На клиенте он пустой — не дай методу вернуть 0 и заблокировать
   вообще всё; фолбэк должен быть 4, как в оригинале.

Проверь после починки: у Мики должно показывать `X/10`, у остальных — их реальные
максимумы (Lucy 10, Kobold 6, Coppie/Momo 8, Slime 6 — сверь по их `getScenes()`).

### 2.2. Что проверить дополнительно

- **Пустые методы-приманки.** Ищи `{ }`, `return false;`, `return null;`, `return 0;` в
  методах, которые по имени должны что-то делать. Именно так уже находились реальные баги:
  `applyClothingAndArmor()` был пустым, и броня на девушках не отображалась вообще;
  `JigglePhysics.update()` был пустым, и модели были каменными.
- **Классы, которые «компилируются, но мертвы».** `OffsetVertexConsumer` существовал и
  выглядел рабочим, но был написан под API до 1.21 (`vertex`/`texture` вместо
  `addVertex`/`setUv`) и не сдвигал ничего. Проверь похожие места.
- **Пакеты, которые никто не отправляет.** `ClothingArmorVisibilityS2CPacket` был
  зарегистрирован, обработчик на клиенте был, а серверная половина отсутствовала. Пройдись
  по `networking/S2C/*` и `networking/C2S/*` и убедись, что у каждого есть и отправитель,
  и получатель. Известно, что `RegisterCustomGirl*C2SPacket` пусты — но они и в оригинале
  никем не отправлялись, их можно просто удалить.
- **Локализация.** Правило проекта: любой новый ключ добавляется **сразу в оба** файла,
  `en_us.json` и `ru_ru.json`. Сейчас паритет полный, не сломай его.
- **Сравнение по строкам вместо предметов.** В `displayArmor` материал брони определяется
  по подстроке в id (`contains("diamond")`) — так в оригинале, оставлено намеренно, но
  учитывай при правках.

## 3. Правила, которые нельзя нарушать

- **Не оставляй заглушек, притворяющихся рабочими.** Если что-то не портируется — лучше
  удали и напиши почему, чем оставь пустой метод, возвращающий `false`. Именно такие
  заглушки и стали источником большинства найденных багов.
- **Проверяй API по исходникам, а не по памяти.** 1.21.1 массово переименовал методы.
  Когда `gh` работает, исходники ванили читаются так:
  ```bash
  gh api "repos/Yeet-Masta/MCP-1.21/contents/src/main/java/net/minecraft/<путь>.java" \
    --jq '.content' | base64 -d | grep -n "чтоИщем"
  ```
  Сорсы NeoForge — `repos/neoforged/NeoForge/contents/...?ref=1.21.1`. Так уже были
  пойманы: `getEyeHeight(Pose)` оказался `final`, `Player` не объявляет attachment
  `PASSENGER` (фолбэк — полная высота 1.8, а не eye height 1.62), `ChunkMap` не шлёт
  игроку пакеты о нём самом.
- **Кости GeckoLib общие между всеми девушками на одном риге.** Всё, что ты меняешь в
  `preRender` (видимость, поворот, масштаб, цвет), нужно **сбрасывать** для тех, к кому
  это не относится. Иначе одна девушка «заражает» всех остальных на том же риге.
- Любая новая цель ИИ обязана проверять `!isPassenger()`, `!isDowned()`, `!isSceneActive()`.
  Ванильные цели этого не умеют — `LookAtPlayerGoal` и `RandomLookAroundGoal` пришлось
  оборачивать подклассом, иначе девушка крутилась на плече у носильщика.
- В `GirlInventoryScreen` максимум 7 кнопок слева и 6 справа, иначе вылезают за экран.
- Отвечай пользователю **по-русски**.
